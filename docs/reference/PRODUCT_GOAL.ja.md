# Product Goal: AIP相当の交換可能なOSS業務基盤

[English](./PRODUCT_GOAL.md)

## 1. 目標

業務の意味と公開契約を自分たちが所有し、状態・検索・認可・Workflow・AI・監査などの実装をPortとAdapterで交換できるOSSプラットフォームを完成させる。Palantir製品の内部実装や画面を複製するのではなく、Ontologyを中心にデータ、ロジック、Action、権限、AI、証拠を結ぶ能力を、検証可能な公開契約として実現する。

最初の完成版は、店舗事業の複雑な通常業務とBCPを、ローカルまたはOSSだけの検証環境で再現・実演できるものとする。実演対象は次の二つである。

1. 商品ロットの回収から、影響店舗・在庫・顧客対応の特定、隔離、承認、代替調達、外部反映、監査までをつなぐ通常業務。
2. WANまたは基幹システム停止中の縮退運転、成功不明な書き戻しの保留、復旧後の照合・重複排除・補償を含むBCP。

## 2. 完成の定義

完成は特定製品の導入数やエージェントの自己申告ではなく、次の受入条件を再現可能な証拠で満たし、最後に実装担当とは別セッションのreviewerが承認した状態とする。

| ID | 受入条件 | 観測可能な合格条件 |
|---|---|---|
| AC-001 | 再現可能な起動 | 新しい環境で文書化した一つの入口からOSS構成を起動し、seed data、health check、デモ前提を自動検査できる。秘密値や有料・独自サービスを必須にしない。 |
| AC-002 | Ontology中心のKernel | 版付きOntology、Objectの取得・有限query・link辿り、期待版付き更新、型付きAction、Action状態、Outbox、監査証拠を公開契約と契約試験付きで提供する。 |
| AC-003 | 認証・認可・委任 | actorとonBehalfOfを信頼境界で確定し、単体取得、一覧、検索、列、Action、AI toolの許可と拒否を同じ業務意味で検査する。障害時はfail closedとし、反例試験を持つ。 |
| AC-004 | 整合性と失敗処理 | 同時更新、同一key再送、異なる入力でのkey再利用、timeout、途中失敗、順序逆転を試験し、重複効果、無記録更新、監査とObjectの不整合を起こさない。 |
| AC-005 | 難解な店舗業務の実演 | 商品回収・代替調達シナリオの正常系、権限拒否、競合、承認待ち、外部反映失敗をUIまたはAPIから実演し、各判断をOntology版・規則版・主体・証拠へ追跡できる。 |
| AC-006 | BCPの実演 | WAN/基幹停止、成功不明、再起動、復旧、照合を注入し、宣言した縮退範囲、RPO/RTO、データ損失、重複、未解決項目を測定する。少なくとも一度はクリーンな復旧演習を完走する。 |
| AC-007 | 交換可能性 | 少なくとも一つの状態を持つ、または意味差のあるAdapterを、shadow比較、差分検査、切替、切戻しまで実演する。共通APIの形だけでなく型、版、認可、再送、移行を照合する。 |
| AC-008 | 運用可能なOSS | 既定構成のライセンス、SBOM、脆弱性、秘密、バックアップ、観測、アップグレード、ロールバック、データ保持を文書と自動検査で扱う。既定経路はOSSとして再配布可能である。 |
| AC-009 | 独立した最終監査 | AC-001〜AC-008を現在のコードと証拠へ一項目ずつ辿り、機械gateと独立reviewerの両方が承認する。未検証、失敗、制約を完成に見せかけない。 |

## 3. アーキテクチャ上の不変条件

- Ontology、Object API、Action、認可合成、Event/Evidence、公開・版管理の意味はプラットフォームが所有し、製品SDKを業務コードへ漏らさない。
- 47責務を47サービスへ分解しない。全責務の判断は残すが、初期構成は少数モジュールとPostgreSQL等の最小OSSから始める。
- AIはActionを提案できるが、実行権限そのものにはならない。Action Engineが実行時の主体、委任、権限、制約、期待版、承認、冪等性を再検査する。
- 外部システムまでのexactly-onceや単一transactionを主張しない。Outbox、少なくとも一回配送、照合、補償で成功不明を扱う。
- 検索索引、ベクトルストア、AI trace、Lineageを、業務状態の正本または監査証拠の代替にしない。
- 既定の開発・デモ経路はOSSのみで再現できる。任意のクラウドや商用Adapterは追加profileとして隔離する。

## 4. 範囲

### 含むもの

- Ontology/Schemaの定義、検証、版、差分、公開、rollbackの最小経路
- Object/Query/Link/Actionの公開APIと型付きclient
- 状態、期待版、Unit of Work、Action log、Outbox、監査証拠
- 認証、関係または属性認可、サービス主体、利用者代理
- Workflow、外部反映、イベント、観測、復旧のうち二つの実演に必要な範囲
- AIを使う場合の権限付き検索、構造化提案、評価、tool制約
- Authoring/Business UIまたは同等の操作面
- 開発環境、試験データ、failure injection、デモrunbook

### 初版の範囲外

- Palantirの全機能、内部実装、ブランド、UIの一対一複製
- 47責務それぞれへの専用製品導入
- 本番店舗や実顧客の個人情報を使う実証
- 法規制、会計、雇用、医療、安全に関する最終判断の自動化
- マルチリージョン本番SLAや無制限のデータ量への性能保証
- 未承認の有料API、クラウド資源、外部への公開・push・デプロイ

## 5. 証拠と品質

受入条件ごとに、仕様、試験、コマンド、入力版、出力hash、実行結果、既知の反例を `evidence/ACCEPTANCE_MATRIX.md` へ結ぶ。検証runは `verification/plan.json` に宣言し、現在の入力hashと一致する成功記録だけを有効とする。正常系だけでなく拒否、競合、重複、timeout、部分障害、復旧を含める。

UIのスクリーンショットやデモ動画は補助証拠であり、状態・監査・試験結果の代わりにはしない。設計文書だけ、空のtest、mockだけ、常に成功するcommandは完成証拠にしない。

## 6. 自律実行の境界

TAKTは、公開情報の調査、OSSの選定案、コード、test、ローカルcontainer、seed data、文書、実行記録の作成と修正を自律的に進めてよい。既存の受入条件を弱めて合格させてはならない。

開発用のモデル呼び出しは、承認済みのLuna/Sol/Astra配分と認証済みCodexアカウント、60工程の初回run内に限り許可する。これは製品の実行時に有料モデルを必須とする許可ではない。新しいAPI契約、追加購入、別課金資源の作成、上限の無条件解除は許可しない。工程数は金額の保証ではなく、利用枠・消費量はrun記録から確認する。

次は推測せず、依存する工程だけを停止して人の判断を求める。

- 実店舗、実顧客、個人情報、機密情報、外部参加者を使う
- 承認済み開発モデル以外の有料サービス、課金される計算、外部環境へのdeploymentを行う
- ライセンスまたは商標上の配布可否が未解決
- データ破壊、既存環境への書き戻し、公開、push、PR、credential変更を行う
- ACの意味、製品の対象利用者、初版のscopeを実質的に変える
- 同じ阻害要因が3回反復し、技術的追加作業では情報が増えない

## 7. 資源と停止条件

初回の自律runは最大60 workflow stepとし、ローカルCPU・memoryで実行できる構成を優先する。大きなモデル学習、長時間負荷試験、大量の外部通信は行わない。step上限到達は未達であり成功ではない。TAKTのcheckpointと報告を残し、原因を確認してから再開する。

完全な製品完成前でも、外部承認、未入手のcredential、ライセンス問題、再現不能なprovider障害で継続不能なら `ABORT` とする。その場合も、通過済みgate、未達AC、再開位置、必要な人の判断を保存する。
